# 一步一步剖析 IAP 升级架构（从演进过程理解设计）

IAP，全称为 **In-Application Programming**，通常翻译为“在应用编程”。

它解决的核心问题是：

> 一台已经运行起来的设备，如何在不使用传统烧录器的情况下，更新自身程序。

为了真正理解 IAP，我们不直接给出最终架构，而是从最简单的方案开始，一步一步推导：

> 每一步遇到什么问题 → 为什么需要改进 → 引入什么机制解决

---

# 一、最原始的升级方式：重新烧录

最初的方式非常直接：

```text
设备
└── 当前程序 V1.0
```

开发出新程序：

```text
firmware_v2.0.bin
```

升级方式：

```text
使用烧录器
    ↓
重新烧录 Flash
```

问题：

* 设备必须拆开或接触调试接口；
* 需要专业工具；
* 已部署设备无法操作；
* 成本极高。

于是我们开始思考：

> 能不能让设备“自己更新自己”？

---

# 二、第一步演进：让固件进入设备

最直观的方式：

```text
U 盘
    ↓
插入设备
    ↓
设备读取文件
    ↓
更新程序
```

问题：

* 很多设备没有 USB Host；
* 设备可能在户外或封闭环境；
* 大规模设备无法人工逐台操作；
* 用户操作容易出错。

于是扩展出更多传输方式：

```text
UART
CAN
RS485
USB
以太网
Wi-Fi
4G
SD 卡
U 盘
外部 Flash
```

这一步解决的是：

> 固件如何进入设备

但新的问题出现：

> 固件进来了，设备如何安全更新自己？

---

# 三、第二步演进：APP 直接覆盖自己（不可行）

最直接的想法：

```text
APP 运行中
    ↓
擦除自身 Flash
    ↓
写入新固件
```

问题：

```text
APP 正在运行
    ↓
擦除 APP Flash
    ↓
代码被删除
    ↓
CPU 无法继续执行
```

结论：

> APP 不能安全地覆盖自己

---

# 四、第三步演进：引入 Bootloader

为了解决“不能自我覆盖”的问题，引入 Bootloader：

```text
Flash
+--------------------------+
| Bootloader               |
+--------------------------+
| Application              |
+--------------------------+
```

启动流程：

```text
上电
  ↓
Bootloader
  ↓
判断是否升级
  ├── 否 → 跳转 APP
  └── 是 → 执行升级
```

这里的关键问题是：

> Bootloader 是如何知道“需要升级”的？

常见做法是通过 **升级标志（Upgrade Flag）或升级状态信息** 来判断，这些信息通常由 APP 在接收并校验完固件后写入非易失性存储（如 Flash、EEPROM 或外部存储）中。

例如：

```text
APP 接收固件完成
      ↓
校验成功
      ↓
写入升级标志（如 magic + state = PENDING）
      ↓
触发系统复位
```

Bootloader 启动后读取该信息：

```text
Bootloader 启动
      ↓
读取升级信息区
      ↓
判断 magic 是否有效
      ↓
判断 state 是否为 PENDING / INSTALLING
```

判断逻辑示例：

```text
if (magic 正确 && state == PENDING)
    → 需要升级
else
    → 正常启动 APP
```

因此：

* **APP 负责“告诉 Bootloader 需要升级”**
* **Bootloader 通过读取持久化标志来做决策**

Bootloader 负责：

* 读取升级标志；
* 判断是否需要升级；
* 擦除 APP；
* 写入新程序；
* 校验；
* 跳转执行。

问题解决：

✅ APP 不再需要覆盖自己
✅ 升级逻辑独立
✅ 升级触发机制清晰（通过标志控制）

但新的问题出现：

> 如果升级过程中断怎么办？

---

# 五、第四步演进：Bootloader 直接接收固件（基础方案）

最简单实现：

```text
进入 Bootloader
      ↓
擦除 APP
      ↓
接收一块
      ↓
写入一块
      ↓
直到完成
```

优点：

* 简单；
* 占用资源少。

问题：

* 升级过程中业务完全停止；
* Bootloader 需要实现通信协议；
* 一旦中断，APP 已被破坏；
* 设备可能变砖。

核心问题：

> 一边接收，一边覆盖，风险极高

---

# 六、第五步演进：引入固件暂存区

为了解决“中断导致设备损坏”，引入暂存区：

```text
Flash
+--------------------------+
| Bootloader               |
+--------------------------+
| APP 运行区               |
+--------------------------+
| 固件暂存区               |
+--------------------------+
| 升级信息区               |
+--------------------------+
```

新流程：

```text
APP 接收固件
      ↓
写入暂存区
      ↓
校验完成
      ↓
设置升级标志
      ↓
重启
      ↓
Bootloader 安装
```

改进：

✅ 接收过程中 APP 仍然运行
✅ 接收失败不会破坏旧程序
✅ Bootloader 不需要复杂通信

但新问题：

* 需要额外存储空间；
* 需要复制一次固件；
* 复制过程中仍可能掉电失败。

---

# 七、第六步演进：引入升级状态机（解决掉电问题）

问题：

> 升级过程中可能掉电或重启

解决方案：

引入升级信息区：

```c
typedef struct {
    uint32_t magic;
    uint32_t state;
    uint32_t firmware_size;
    uint32_t firmware_crc32;
    uint32_t received_size;
    uint32_t copied_size;
} iap_metadata_t;
```

状态机：

```text
EMPTY
  ↓
DOWNLOADING
  ↓
DOWNLOADED
  ↓
VERIFIED
  ↓
PENDING
  ↓
INSTALLING
  ↓
INSTALLED
  ↓
CONFIRMED
```

作用：

✅ 支持断点恢复
✅ 支持掉电恢复
✅ 支持跨重启流程

本质：

> IAP 是一个持久化状态机

---

# 八、第七步演进：引入固件校验（解决错误固件问题）

问题：

* 数据损坏；
* 固件不完整；
* 固件版本错误；
* 固件被篡改。

解决方案：

引入固件头：

```text
+--------------------------+
| Firmware Header          |
+--------------------------+
| Firmware Data            |
+--------------------------+
| Hash / Signature         |
+--------------------------+
```

结构：

```c
typedef struct {
    uint32_t magic;
    uint32_t image_size;
    uint32_t image_crc32;
    uint8_t  image_sha256[32];
} iap_image_header_t;
```

校验内容：

```text
Magic
大小
CRC32
SHA256
签名
```

作用：

✅ 防止损坏固件运行
✅ 防止错误版本
✅ 支持安全升级

---

# 九、第八步演进：引入 A/B 双镜像（解决最终可靠性问题）

问题：

> 即使有暂存区，复制过程中仍可能失败

解决方案：

```text
Flash
+--------------------------+
| Bootloader               |
+--------------------------+
| APP A                    |
+--------------------------+
| APP B                    |
+--------------------------+
| Metadata                 |
+--------------------------+
```

流程：

```text
当前运行 A
      ↓
写入 B
      ↓
校验成功
      ↓
标记 pending = B
      ↓
重启
      ↓
尝试运行 B
```

成功：

```text
active = B
confirmed = true
```

失败：

```text
回滚到 A
```

优势：

✅ 永远保留一个可用版本
✅ 自动回滚
✅ 不会变砖

---

# 十、第九步演进：引入运行确认与喂狗标志（判断是否变砖）

问题：

> 即使切换到了新 APP，也无法保证它真的“能正常运行”

例如：

* 程序启动后死循环；
* 初始化失败；
* 看门狗未喂导致复位；
* 系统卡死但未崩溃；
* 功能异常但仍在运行。

因此需要进一步判断：

> 新 APP 是否真正“活着”并且“功能正常”

---

## 1. 引入“喂狗标志”（Alive Flag）

设计思路：

* Bootloader 启动新 APP 后，必须要求 APP 在规定时间内：

  * 正常运行；
  * 喂狗（Watchdog Feed）；
  * 并写入一个“运行标志位”。

流程：

```text
Bootloader 启动新 APP
      ↓
启动看门狗（WDT）
      ↓
APP 初始化
      ↓
APP 喂狗 + 写入 alive_flag = OK
```

如果发生以下情况：

```text
APP 未启动
APP 卡死
APP 未喂狗
APP 未写标志
```

则：

```text
看门狗复位
      ↓
Bootloader 再次启动
      ↓
检测 alive_flag 未置位
      ↓
判定新 APP 异常
      ↓
执行回滚
```

---

## 2. 引入“功能确认标志”（Functional Flag）

仅仅“活着”还不够，还需要确认：

> 功能是否正常

例如：

* 外设初始化成功；
* 通信正常；
* 关键任务运行正常；
* 自检通过。

APP 在运行一段时间后：

```text
功能自检完成
      ↓
写入 functional_flag = OK
```

Bootloader 在下次启动时判断：

```text
if (alive_flag == OK && functional_flag == OK)
    → 确认升级成功
else
    → 回滚旧版本
```

---

## 3. 标志位设计示例

```c
typedef struct {
    uint32_t magic;
    uint32_t active_slot;
    uint32_t pending_slot;

    uint32_t alive_flag;       // 是否成功喂狗并运行
    uint32_t functional_flag; // 功能是否正常

} boot_control_t;
```

---

## 4. 完整判断逻辑

```text
Bootloader 启动
      ↓
检测 pending_slot
      ↓
尝试启动新 APP
      ↓
等待 APP 喂狗 + 写 alive_flag
      ↓
等待 APP 写 functional_flag
```

判断：

```text
alive_flag == OK ?
    否 → 回滚
    是 → 继续

functional_flag == OK ?
    否 → 回滚
    是 → 确认升级成功
```

---

## 5. 这一演进解决的问题

✅ 能检测“程序是否真正运行”
✅ 能检测“程序是否卡死”
✅ 能检测“程序是否功能正常”
✅ 能避免“启动成功但实际不可用”的情况

本质：

> 从“能启动”升级为“能稳定运行”

---

# 十一、演进总结

整个 IAP 架构是逐步演进出来的：

```text
重新烧录
    ↓
固件传输（UART / U盘 / 网络）
    ↓
APP 自更新（失败）
    ↓
引入 Bootloader（通过升级标志判断是否升级）
    ↓
Bootloader 直接升级（风险高）
    ↓
引入暂存区
    ↓
引入状态机
    ↓
引入校验机制
    ↓
引入 A/B 双镜像
    ↓
引入运行确认（喂狗 + 功能标志）
```

核心思想：

> 每一步都是为了解决上一阶段的问题

---

# 十二、IAP 不是通信方式

很多人会说：

```text
UART IAP
CAN IAP
Ethernet IAP
```

实际上：

```text
UART ─┐
CAN ──┤
TCP ──┼──→ IAP Core
USB ──┤
File ─┘
```

区别只是：

> 固件怎么进来

IAP 核心始终一致：

```text
接收
保存
校验
标记
重启
安装
运行
确认
```

---

# 十三、通用 IAP 架构

```text
┌────────────────────────────┐
│ 固件来源（PC / U盘 / 网络） │
└──────────────┬─────────────┘
               │
┌──────────────▼─────────────┐
│ Transport（UART/CAN/TCP）  │
└──────────────┬─────────────┘
               │
┌──────────────▼─────────────┐
│ IAP Core（状态机）         │
└──────────────┬─────────────┘
               │
┌──────────────▼─────────────┐
│ Verify（CRC/签名）         │
└──────────────┬─────────────┘
               │
┌──────────────▼─────────────┐
│ Storage（Flash）           │
└──────────────┬─────────────┘
               │
┌──────────────▼─────────────┐
│ Boot Control              │
└────────────────────────────┘
```

---

# 十四、完整升级闭环

```text
接收固件
    ↓
写入存储
    ↓
校验
    ↓
设置 pending
    ↓
重启
    ↓
Bootloader 安装
    ↓
启动新 APP
    ↓
喂狗确认（alive）
    ↓
功能确认（functional）
    ↓
最终确认成功
```

失败：

```text
未喂狗 / 未确认
   ↓
回滚
```

---

# 十五、最终结论

IAP 的核心不是通信接口，而是：

```text
Bootloader
Flash 布局
升级状态机
固件校验
启动控制
运行确认机制
回滚机制
```
