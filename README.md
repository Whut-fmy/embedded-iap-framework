# embedded-iap-framework
基于 STM32 的 CAN IAP Bootloader，支持固件分包传输、CRC 校验、升级状态管理、APP 跳转和失败恢复。一个可移植的嵌入式 IAP 固件升级框架，支持 UART、CAN、以太网、USB 和外部存储介质。
# 一步一步剖析 IAP 升级架构

IAP，全称为 **In-Application Programming**，通常翻译为“在应用编程”。

它主要解决的问题是：

> 一台已经运行起来的设备，如何在不使用传统烧录器重新烧录的情况下，更新自身内部的程序。

假设现在有一台已经交付使用的设备，设备中运行的是旧版本程序：

```text
设备
└── 当前程序 V1.0
```

现在我们开发了一个新的程序：

```text
firmware_v2.0.bin
```

那么第一个问题就是：

> 怎样把这个新固件更新到设备中？

一开始，我们可能会想到：

```text
把固件放入 U 盘
    ↓
将 U 盘插入设备
    ↓
设备读取固件文件
    ↓
更新内部程序
```

这种方式确实可以实现程序升级。

但是，并不是所有设备都带有 USB Host 接口，也不是所有设备都方便插入 U 盘。

于是，我们还可以通过其他方式将固件传输到设备：

```text
UART
CAN
RS485
USB
以太网
Wi-Fi
4G
SD 卡
U 盘
外部 Flash
```

这些方式虽然不同，但本质上都只是在解决一个问题：

> 新固件如何进入设备。

当固件已经进入设备之后，还需要解决另外一个更加关键的问题：

> 设备如何使用这个固件更新自身程序。

这才是 IAP 真正关注的核心。

---

# 一、IAP 不是某一种通信方式

很多项目会出现下面这些名称：

```text
UART IAP
CAN IAP
USB IAP
Ethernet IAP
```

这些名称容易让人误以为存在很多种不同的 IAP。

实际上，它们的主要区别只在于固件传输方式不同。

```text
UART ─────┐
CAN ──────┤
USB ──────┼──→ 固件数据 ──→ IAP 核心
Ethernet ─┤
U盘 ──────┘
```

进入 IAP 核心之后，后续流程基本相同：

```text
接收固件
    ↓
保存固件
    ↓
校验固件
    ↓
设置升级标志
    ↓
重新启动
    ↓
安装或切换新固件
    ↓
运行新程序
```

因此，通用 IAP 框架不应该与 UART、CAN 或以太网中的某一种接口绑定。

通信接口只负责把数据送进来。

IAP 核心负责处理升级。

---

# 二、先区分固件传输和固件安装

一个完整的 IAP 升级过程可以分成两个阶段。

## 1. 固件传输阶段

这个阶段解决：

> 新固件如何进入设备。

例如：

```text
PC 上位机
    │
    │ UART / CAN / USB / TCP
    ▼
设备
```

或者：

```text
U 盘 / SD 卡
    │
    ▼
设备读取固件文件
```

这一阶段可能包含：

* 升级命令；
* 固件分包；
* 包序号；
* ACK 和 NACK；
* 超时重传；
* 下载进度；
* 固件长度；
* 断点续传。

## 2. 固件安装阶段

这个阶段解决：

> 设备收到新固件后，如何安全地替换旧程序。

主要包括：

* 固件写入位置；
* Flash 擦除；
* 固件完整性校验；
* 升级状态保存；
* Bootloader 判断；
* 新程序启动；
* 升级失败恢复。

因此：

```text
通信接口负责传输；
IAP 负责安装和更新。
```

---

# 三、为什么 APP 不能简单地覆盖自己

假设设备的 Flash 中只有一个 APP：

```text
Flash
+--------------------------+
| Application V1.0         |
| 当前 CPU 正在执行这里     |
+--------------------------+
```

如果 APP 直接擦除自己所在的区域：

```text
APP 正在运行
    ↓
擦除 APP Flash
    ↓
当前程序代码被删除
    ↓
CPU 无法继续执行
```

因此，正在运行的 APP 通常不能直接无保护地覆盖自身。

这就需要引入一个独立的小程序：

```text
Bootloader
```

---

# 四、引入 Bootloader

重新划分设备内部 Flash：

```text
Flash 低地址
+--------------------------+
| Bootloader               |
+--------------------------+
| Application              |
+--------------------------+
Flash 高地址
```

芯片复位以后，不再直接进入 APP，而是先执行 Bootloader：

```text
芯片上电或复位
      ↓
Bootloader
      ↓
检查升级状态
  ┌───┴────────┐
  │            │
无升级        有升级
  │            │
跳转 APP      执行升级
```

Bootloader 通常负责：

* 判断是否存在升级请求；
* 判断 APP 是否有效；
* 擦除 APP 区；
* 写入新程序；
* 校验写入结果；
* 选择启动镜像；
* 设置中断向量表；
* 跳转到 APP；
* 处理升级失败恢复。

Bootloader 是 IAP 系统中非常重要的一部分。

---

# 五、新固件应该存放在哪里

假设当前 APP V1.0 正在运行，设备开始接收新固件 V2.0。

这时又出现一个问题：

> 新固件在接收过程中放在哪里？

如果设备一边接收，一边直接覆盖当前 APP，那么只要出现以下情况：

* 通信中断；
* 设备断电；
* 固件错误；
* Flash 写入失败；

当前旧程序就可能已经被破坏，而新程序又没有写完整，最终设备无法启动。

因此，通常需要给新固件准备一个临时存储区。

```text
Flash / 外部存储器
+--------------------------+
| Bootloader               |
+--------------------------+
| APP 运行区 V1.0          |
+--------------------------+
| 固件暂存区 V2.0          |
+--------------------------+
| 升级信息区               |
+--------------------------+
```

固件暂存区可以位于：

```text
内部 Flash
外部 SPI Flash
QSPI Flash
eMMC
SD 卡
U 盘
文件系统
```

设备首先将完整的新固件保存到暂存区。

旧 APP 在这个过程中仍然可以继续运行。

# 六、APP 和 Bootloader 如何分工

一种常见的 IAP 架构是：

## APP 负责接收固件

APP 通常已经具备完整的通信能力，因此可以负责：

* UART 通信；
* CAN 通信；
* TCP/IP 通信；
* USB 通信；
* 文件系统访问；
* U 盘或 SD 卡读取；
* 固件分包接收；
* 下载进度显示。

APP 的工作流程：

```text
检测到升级请求
      ↓
接收固件信息
      ↓
擦除固件暂存区
      ↓
分块接收固件
      ↓
写入暂存区
      ↓
校验完整固件
      ↓
设置升级标志
      ↓
系统复位
```

## Bootloader 负责安装固件

设备重启后，Bootloader 运行：

```text
Bootloader 启动
      ↓
读取升级标志
      ↓
发现待安装固件
      ↓
检查固件是否合法
      ↓
擦除 APP 运行区
      ↓
复制新固件到 APP 区
      ↓
校验复制结果
      ↓
清除升级标志
      ↓
跳转新 APP
```

因此：

```text
APP 负责“下载或接收”；
Bootloader 负责“安装和启动”。
```

# 七、为什么需要升级信息区

设备在升级过程中可能会多次复位，甚至可能突然掉电。

因此，升级状态不能只保存在 RAM 中。

需要将升级信息保存到 Flash、EEPROM、外部 Flash 或其他非易失性存储器中。

例如：

```c
typedef struct {
    uint32_t magic;
    uint32_t state;
    uint32_t firmware_size;
    uint32_t firmware_version;
    uint32_t firmware_crc32;
    uint32_t received_size;
    uint32_t copied_size;
} iap_metadata_t;
```

升级状态可以定义为：

```text
EMPTY
DOWNLOADING
DOWNLOADED
VERIFIED
PENDING
INSTALLING
INSTALLED
CONFIRMED
FAILED
```

整个状态转换过程：

```text
EMPTY
  ↓
DOWNLOADING
  ↓
DOWNLOADED
  ↓
VERIFIED
  ↓
PENDING
  ↓ 设备重启
INSTALLING
  ↓
INSTALLED
  ↓
CONFIRMED
```

因此，IAP 并不是简单调用一次 Flash 写入函数。

它实际上是一个：

> 能够跨越复位、掉电和异常的持久化状态机。

---

# 八、为什么需要校验固件

设备收到新固件后，不能立即认为升级成功。

固件可能存在：

* 数据丢失；
* 数据重复；
* 数据错乱；
* 固件没有接收完整；
* Flash 写入错误；
* 固件版本错误；
* 固件与当前硬件不匹配；
* 固件被人为篡改。

因此，需要为固件添加固件头。

```text
+--------------------------+
| Firmware Header          |
+--------------------------+
| Firmware Data            |
+--------------------------+
| Hash / Signature         |
+--------------------------+
```

固件头可以包含：

```c
typedef struct {
    uint32_t magic;
    uint16_t header_version;
    uint16_t hardware_id;

    uint32_t firmware_version;
    uint32_t image_size;

    uint32_t load_address;
    uint32_t entry_address;

    uint32_t image_crc32;
    uint8_t  image_sha256[32];

    uint32_t flags;
} iap_image_header_t;
```

设备至少需要检查：

```text
Magic 是否正确
硬件型号是否匹配
固件大小是否正确
固件版本是否允许
CRC32 是否一致
APP 地址是否合法
APP 入口地址是否合法
```

对于安全要求较高的产品，还需要检查：

```text
SHA-256
数字签名
版本防回退
公钥合法性
```

CRC32 只能检查固件是否意外损坏。

数字签名才能证明：

> 该固件是否由可信发布者生成。

# 九、IAP 架构的逐步演进：从最简单方案开始

在理解更复杂的 IAP 设计之前，可以先从最基础的实现方式出发，一步一步推导出为什么需要更完善的架构。

最简单的 Flash 布局如下：

```text
+--------------------------+
| Bootloader               |
+--------------------------+
| Application              |
+--------------------------+
```

在这种设计中，升级流程通常是：

```text
进入 Bootloader
      ↓
擦除 APP 区
      ↓
接收一块固件
      ↓
写入一块固件
      ↓
直到接收完成
      ↓
校验
      ↓
跳转 APP
```

这种方式的特点是：

* 实现非常简单；
* Flash 占用最少；
* 适合资源受限的 MCU。

但随着实际使用，很快会暴露出一些问题：

* 升级过程中业务完全停止；
* Bootloader 需要实现完整通信协议；
* 一旦中途失败，APP 可能已经被破坏；
* 容错能力较弱。

正是这些问题，推动我们继续改进架构。

---

# 十、为了解决中断风险，引入固件暂存区

在上一种方案中，最大的问题是：

> 一边接收，一边覆盖当前 APP，一旦失败就可能导致设备无法启动。

为了解决这个问题，可以引入一个新的区域：

```text
+--------------------------+
| Bootloader               |
+--------------------------+
| APP 运行区               |
+--------------------------+
| 固件暂存区               |
+--------------------------+
| 升级信息区               |
+--------------------------+
```

新的思路是：

* 当前 APP 负责接收固件；
* 固件先写入“暂存区”，而不是直接覆盖 APP；
* 完整接收并校验成功后，再进行安装。

流程变为：

```text
上位机或存储设备
       ↓
当前 APP
       ↓
固件暂存区
       ↓
设置升级标志
       ↓
设备复位
       ↓
Bootloader
       ↓
复制到 APP 运行区
```

这样带来的改进是：

* 接收过程中旧 APP 仍然可以运行；
* 接收失败不会破坏当前程序；
* Bootloader 可以保持简单，不需要复杂通信；
* 更适合文件系统、以太网、U 盘等场景。

但新的问题也随之出现：

* 需要额外的存储空间；
* 固件需要复制一次；
* 在复制过程中仍然需要考虑掉电风险。

于是，我们继续思考：

> 能不能在任何时候都保留一份完整可用的程序？

---

# 十一、为了进一步提高可靠性，引入 A/B 双镜像

为了解决“复制过程中仍可能失败”的问题，可以进一步演进为双镜像结构：

```text
+--------------------------+
| Bootloader               |
+--------------------------+
| APP A                    |
+--------------------------+
| APP B                    |
+--------------------------+
| Boot Control Metadata    |
+--------------------------+
```

核心思想是：

* 始终保留两份完整的应用程序；
* 当前运行其中一份；
* 新固件写入另一份；
* 切换时具备回滚能力。

例如当前运行 APP A：

```text
active_slot = A
```

设备将新固件写入 APP B：

```text
APP A：当前正在运行
APP B：接收新固件
```

当固件 B 校验成功后：

```text
pending_slot = B
```

设备重启，Bootloader 尝试启动 APP B。

如果运行正常：

```text
active_slot = B
confirmed = true
```

如果运行失败：

```text
Bootloader 回退到 APP A
```

这种设计带来的优势是：

* 始终保留一份可用固件；
* 升级失败不会导致设备变砖；
* 支持自动回滚；
* 非常适合无人值守和远程设备。

因此，它常用于：

* 高可靠设备；
* 工业控制系统；
* 远程部署设备；
* 对稳定性要求极高的产品。

---

通过这样的逐步演进可以看到：

```text
直接覆盖 APP
    ↓
引入暂存区避免破坏旧程序
    ↓
引入双镜像实现可回滚
```

IAP 架构并不是一开始就复杂，而是随着对可靠性要求的提升，一步一步自然发展出来的。

# 十二、为什么 UART、CAN、以太网最终可以共用同一个 IAP Core

不同通信接口存在不同特点：

```text
UART：
字节流，需要解决帧边界和粘包问题。

CAN：
帧长度较小，需要分片和重组。

TCP：
字节流，需要长度字段和接收缓存。

U盘：
从文件系统读取固件。

以太网：
可以通过 TCP、HTTP 或其他协议获取固件。
```

但是这些差异都应该由传输适配层处理。

```text
UART Transport ───┐
CAN Transport ────┤
TCP Transport ────┼──→ IAP Core
USB Transport ────┤
File Transport ───┘
```

IAP Core 不需要知道固件来自哪里。

它只需要提供统一接口：

```c
int iap_begin(const iap_image_info_t *info);

int iap_write(uint32_t offset,
              const uint8_t *data,
              uint32_t length);

int iap_finish(void);

int iap_verify(void);

int iap_activate(void);

int iap_abort(void);
```

不同接口最终都调用：

```c
iap_write(offset, data, length);
```

这就是通用 IAP 框架的核心思想。

# 十三、通用 IAP 架构

一个完整的通用 IAP 框架可以分成以下几个部分：

```text
┌──────────────────────────────────┐
│        固件发送端或固件来源       │
│ PC、U盘、SD卡、服务器、外部Flash  │
└────────────────┬─────────────────┘
                 │
┌────────────────▼─────────────────┐
│           传输适配层              │
│ UART、CAN、USB、TCP、文件系统      │
└────────────────┬─────────────────┘
                 │
┌────────────────▼─────────────────┐
│             IAP Core             │
│ 状态机、偏移、进度、错误处理       │
└────────────────┬─────────────────┘
                 │
┌────────────────▼─────────────────┐
│           固件校验层              │
│ CRC32、SHA-256、数字签名           │
└────────────────┬─────────────────┘
                 │
┌────────────────▼─────────────────┐
│           存储适配层              │
│ 内部Flash、SPI Flash、eMMC         │
└────────────────┬─────────────────┘
                 │
┌────────────────▼─────────────────┐
│          Boot Control            │
│ 安装、选择、跳转、确认、回滚       │
└──────────────────────────────────┘
```

各层职责如下：

```text
Transport：
负责固件怎么进来。

IAP Core：
负责升级过程如何进行。

Storage：
负责固件写到哪里。

Verify：
负责判断固件是否合法。

Boot Control：
负责最终启动哪个程序。
```

# 十四、完整 IAP 升级闭环

一次完整的 IAP 升级，不应该只到“固件写入完成”为止。

完整流程应该是：

```text
发现或接收到新固件
        ↓
检查固件基本信息
        ↓
开始升级会话
        ↓
擦除目标区域
        ↓
分块接收或读取固件
        ↓
写入存储区域
        ↓
校验固件完整性
        ↓
设置 pending 标志
        ↓
设备复位
        ↓
Bootloader 安装或切换镜像
        ↓
启动新 APP
        ↓
新 APP 试运行
        ↓
确认升级成功
```

如果新 APP 启动失败：

```text
启动失败
   ↓
Bootloader 检测未确认
   ↓
回退旧固件
```

因此：

```text
固件接收完成
    ≠
固件安装成功
    ≠
新程序运行成功
```

真正的升级成功必须包含：

```text
接收成功
校验成功
安装成功
启动成功
运行确认成功
```

# 十五、一步一步推导 IAP 的核心逻辑

整个 IAP 架构可以按照下面的逻辑逐步推导出来：

```text
设备需要更新程序
        ↓
最开始想到重新使用烧录器烧录
        ↓
设备已经交付，重新烧录不方便
        ↓
想到使用 U盘、UART、CAN 等传输固件
        ↓
这解决了“固件如何进入设备”
        ↓
但还没有解决“设备如何更新自己”
        ↓
APP 不能安全地直接覆盖自己
        ↓
引入 Bootloader
        ↓
为了防止传输失败破坏旧 APP
        ↓
引入固件暂存区
        ↓
为了记录跨复位的升级过程
        ↓
引入升级信息区和状态机
        ↓
为了防止错误固件启动
        ↓
引入 CRC、Hash 和数字签名
        ↓
为了防止新程序启动失败
        ↓
引入试运行、确认和回滚
        ↓
为了兼容不同通信接口
        ↓
抽象 Transport、Storage 和 IAP Core
```

最终可以得出：

> IAP 的核心不是 UART、CAN 或以太网，而是 Bootloader、Flash 布局、升级状态机、固件校验、启动切换和失败恢复。

---

# 十六、通用 IAP 项目的最终目标

本项目不局限于某一种固件传输接口。

项目支持的固件来源可以包括：

```text
UART
CAN
CAN FD
RS485
USB
以太网
Wi-Fi
4G
U盘
SD卡
外部 Flash
```

项目需要统一的部分包括：

```text
固件包格式
升级命令
固件元信息
升级状态机
错误码
存储接口
完整性校验
启动控制
升级确认
失败回滚
```

最终实现：

```text
不同固件来源
      ↓
不同传输适配器
      ↓
统一 IAP Core
      ↓
统一存储接口
      ↓
统一 Boot Control
```

这基本就是一个比较通用、也方便后续扩展的 IAP 固件升级框架了。
